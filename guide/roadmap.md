## 一、总体思路

### 1.1 三条原则

1. **先正确，后性能**。每个阶段都要先证明"不超卖、不丢单、不重复"，再谈 QPS。参考项目最大的问题就是性能优化走在了一致性前面。
2. **渐进式演进，每个阶段都能跑、能测、能压**。从最朴素的 MySQL 同步下单开始，一步步加 Redis、MQ。每加一层都留下一组压测数据，最后就有一条"为什么要这样设计"的 A/B 证据链，面试时最有说服力。
3. **每个阶段都有可验证的验收标准**。用测试和对账脚本来证明，不靠"感觉没问题"。

### 1.2 架构演进总览

```
阶段 2  同步版        Client → API → MySQL（事务：扣库存 + 建单）

阶段 3  Redis 拦截    Client → API → Redis Lua 预占 → MySQL（同步落库）

阶段 4  异步削峰      Client → API → Redis Lua 预占 → MQ ──→ Worker → MySQL
                         ↑                                     │
                         └──── 轮询结果（订单号） ←────────────┘

阶段 5  订单闭环      + 支付 / 取消状态机 + 超时取消 + 库存补偿任务

阶段 6~8              + 限流防刷 + 监控对账 + 压测优化
```

### 1.3 阶段一览

| 阶段 | 名称 | 核心产出 | 重要度 | 状态 |
|---|---|---|---|---|
| 0 | 工程骨架 | 能一键启动依赖、跑起服务、跑测试 | 必做 | ✅ 已完成（tag `stage-0`） |
| 1 | 基础业务域 | 用户 / 商品 / 活动 / 订单模型和基础接口 | 必做 | ▶ 当前阶段，见 `stage1-todolist.md` |
| 2 | 同步秒杀 v1 | 基于 MySQL 的无超卖下单，并发测试，性能基线 | 必做 | |
| 3 | Redis 前置拦截 | Lua 原子预占 + 安全预热 + 对账 v1 | 必做 | |
| 4 | 异步削峰 | MQ 可靠投递 + 幂等消费 + 结果查询 | **核心** | |
| 5 | 订单生命周期 | 状态机 CAS + 超时取消 + 可靠库存补偿 | **核心** | |
| 6 | 流量治理与防刷 | 多层限流、本地缓存、降级 | 推荐 | |
| 7 | 可观测性与质量门禁 | 指标 / 日志 / 对账告警 / CI | 推荐 | |
| 8 | 压测优化与成果沉淀 | 正确口径的压测报告、优化 A/B、文档、简历条目 | 必做 | |

> 时间紧时的最小可用集：**0 → 1 → 2 → 3 → 4 → 5 → 8**。这几个阶段做扎实，比把所有阶段都做浅更有价值。

### 1.4 贯穿全程的约定

这一节是阶段 0 完成后补上的。前三条来自已经落地的代码，后面所有阶段都按它来。

**（1）技术选型（阶段 0 已落地）**

| 领域 | 选型 |
|---|---|
| HTTP | Gin，外面包一层 `http.Server` 以支持优雅停机 |
| 数据库访问 | GORM（`gorm.io/gorm` + `gorm.io/driver/mysql`，底层 `go-sql-driver/mysql`） |
| Redis | `redis/go-redis` v9 |
| 日志 | 标准库 `log/slog`，`request_id` 通过 context 自动带入 |
| 配置 | 代码默认值 → YAML → 环境变量；密钥只走环境变量 |
| 表结构 | golang-migrate + 纯 SQL 迁移文件 |
| 测试与检查 | 标准库 `testing` + `httptest`，集成测试用 build tag `integration`；golangci-lint v2 |

**（2）GORM 使用约定**

最初推荐 `database/sql` + sqlx，理由是后面大量逻辑依赖"带条件的 `UPDATE` + 检查影响行数"，手写 SQL 最直观。现在选了 GORM，这个要求不变，只是换成靠约定来保证：

- **表结构只由迁移文件管理**，不用 `AutoMigrate`
- **扣库存、状态流转一律用带条件的 `UPDATE`，并检查 `RowsAffected`**。不允许"先查出来、改内存里的字段、再 `Save` 回去"
- **不用 `Save` 做更新**（它是"全字段覆盖 + 不存在就插入"）；部分更新用 `Updates(map)` 或 `Select(...).Updates(...)`
- **所有数据库调用都带 `WithContext(ctx)`**，ctx 从 handler 一路传到 repository
- **开启 `TranslateError`**，用 `errors.Is(err, gorm.ErrDuplicatedKey)` 识别唯一键冲突
- **业务表不用软删除**（`gorm.DeletedAt`），不用 Hook 和自动保存关联
- **写出来的每条 GORM 语句都要知道它生成的 SQL**：开发环境打开 SQL 日志，或用 `db.ToSQL(...)` 查看
- 热点路径上如果 GORM 写法绕，直接 `db.Exec` / `db.Raw` 写原生 SQL，不算违规

**（3）两个不要混淆的标识**

| 标识 | 谁生成 | 用途 |
|---|---|---|
| `request_id` | 每个 HTTP 请求一个；客户端可以通过 `X-Request-ID` 自己指定 | **只用于日志追踪**（阶段 0 已实现） |
| 订单号（`orders.id`） | 服务端在受理下单请求时生成，全局唯一 | **业务幂等键**：Redis 预占标识、MQ 消息身份、订单主键 |

本文早期版本把业务幂等键也叫 `request_id`，容易让人顺手拿可被客户端随意指定的 `X-Request-ID` 去做幂等，所以改名。

**（4）时间**

- 业务判断（活动是否开始、订单是否超时）只用**应用进程的时钟**，把 `now` 当参数传进 SQL，不在 SQL 里写 `NOW()`
- 应用的 `loc` 必须和数据库会话时区一致，并且写死，不依赖机器的本地时区（阶段 1 Step 3 落实）

## 二、各阶段说明

### 阶段 0：工程骨架

**目标**：搭好一个干净、可重复启动的工程底座，后面只往里加业务。

**要做的事**
- Go module 初始化，确定分层：`cmd/api`、`cmd/worker`（先留空）、`internal/{handler,service,repository,model,...}`、`pkg/`
- 配置：配置文件 + 环境变量覆盖，密钥类配置只从环境变量读取
- 结构化日志（`log/slog` 或 zap）
- `docker-compose`：先只放 MySQL 和 Redis（Kafka 到阶段 4 再加）
- 数据库迁移工具（如 golang-migrate），表结构用版本化的 SQL 管理
- 统一响应格式和错误码、`/healthz` 健康检查
- 优雅停机骨架（监听信号 → 停止接收请求 → 等在途请求完成 → 关闭资源）
- Makefile：`up / down / run / test / lint`

**验收标准**
- 新机器上 `make up && make run` 就能启动服务，`/healthz` 能返回 MySQL、Redis 连通状态
- `go test ./...` 可以运行（哪怕还没有测试）

**参考项目**：分层结构和"环境变量覆盖敏感配置"可以借鉴；**不要**照搬"启动时清空 Redis / 启动时全量预热"（R06）。

**完成情况（2026-11-13）**：已完成，`implement/` 打了 tag `stage-0`。有四件事留到阶段 1 开头处理（`stage1-todolist.md` 的 Step 0、2、3）：
- `make test-integration` 在 `stage-0` 上稳定失败（测试清理顺序的问题，业务代码没问题）
- 错误码放在 `internal/server` 包里，service 层一出现就会碰到依赖方向问题
- GORM 用的是默认日志，不走 slog、不带 `request_id`，出错时会把参数值原样打出来
- DSN 用 `loc=Local`，时区取决于程序跑在哪台机器上

### 阶段 1：基础业务域

**目标**：把秒杀之外的基础业务做完，并把**数据模型和分层**设计对，后面会一直依赖它。

**关键设计决策**（每一条的理由和思考题在 `stage1-todolist.md`）
- **账号**：一张 `users` 表 + `role` 字段，不分"用户表"和"管理员表"。两类账号共用一个 ID 空间，从结构上消除 R13
- **库存归属**：库存属于**活动**（`seckill_activities.total_stock` / `available_stock`），商品表只有基本信息和原价。避开"库存挂在商品上、后台可以直接覆盖"（R11）
- **活动状态**：数据库只存人为控制的状态（草稿 / 已发布 / 已下线）；"未开始 / 进行中 / 已结束"由时间窗现算，不落库。**发布即冻结**——发布后库存、限购、时间窗、价格都不能再改（阶段 3 的预热依赖这个不变量）
- **订单号**：`orders.id` 就是订单号，由应用生成，不是自增
- **金额**：整数分；订单保存下单时的单价和商品名快照（R16）
- **订单状态与超时**：状态值从 1 开始（0 留给"没赋值"）；`expire_at` 列 + `(status, expire_at)` 索引支撑阶段 5 的超时扫描
- **不建物理外键、不做软删除、不提供删除接口**

**要做的事**
- 分层落地：`handler → service → repository`；错误码下沉为不依赖任何内部包的叶子包
- GORM 接入 slog、开启错误翻译；时区约定落地
- 四张业务表的迁移文件
- 用户注册 / 登录：bcrypt 存密码，JWT 签发；Token 中带 `role`，**普通用户接口和管理接口各自校验角色**（R13）
- 管理端接口（只要 API，不要前端）：商品增改查；活动的创建、草稿编辑、发布、下线
- 公开接口：已发布活动的列表和详情
- 用户订单查询接口：列表用游标分页；只能查到自己的订单
- 管理员账号用命令行工具创建，不提供公开入口

**本阶段不做**：邮箱验证码、图形验证码、找回密码、用户封禁、统计面板、前端页面。参考项目里有这些，但和秒杀主线无关。

**验收标准**
- 用 curl 或 `.http` 文件能跑通"注册 → 登录 → 管理员建商品和活动 → 发布 → 公开查询"
- repository 层有针对真实 MySQL 的测试；鉴权矩阵（没带 Token、角色不符、访问别人的订单）有自动化测试
- `make test`、`make test-integration`、`make lint` 全部通过

### 阶段 2：同步秒杀 v1，先在 MySQL 上保证正确

**目标**：只用 MySQL 实现一个正确的秒杀，理解超卖的根源，并拿到第一组性能基线。

**要做的事**
- **订单号生成器**：雪花算法一类的趋势递增 ID。要处理同一毫秒内序号用完、时钟回拨；worker id 先做成配置项
- **事务边界**：扣库存和建订单在同一事务，事务由 service 层发起。先想清楚"一个事务里要调用两个 repository"在 GORM 下怎么组织（`db.Transaction` + 把事务句柄传下去）
- 先**故意**写一版"先查库存再扣减"，用并发测试复现超卖
- 改成正确的实现，并对比几种方案：
  - 条件更新：`UPDATE ... SET available_stock = available_stock - ? WHERE id = ? AND available_stock >= ?`（GORM 里用 `gorm.Expr`）
  - 乐观锁（version）。需要加一列，可以只在实验分支上做
  - 悲观锁（`SELECT ... FOR UPDATE`，GORM 里是 `clause.Locking`）
- 限购由数据库约束或事务内校验保证。三个坑已经在 MySQL 8.0.46 上复现过，设计时绕开：
  - **快照读**：可重复读级别下，事务里只要**先执行过一次普通 `SELECT`**，后面再查"这个用户已经买了几件"读到的就是旧快照，看不到别的事务刚提交的订单，限购会被并发请求绕过
  - **间隙锁死锁**：对"还不存在的订单行"做 `SELECT ... FOR UPDATE` 再 `INSERT`，两个**不同用户**的事务会互相死锁（错误号 1213）
  - **外键死锁**：如果订单表对活动表建了物理外键，"先插订单、再扣库存"会在热点行上大面积死锁（8 并发各 30 次，240 个事务里 201 个死锁）；去掉外键后为 0。阶段 1 不建物理外键，这是原因之一
- 编写并发测试：库存 N、并发请求 M（M ≫ N），断言**库存不为负，订单数量与库存减少量一致，每个用户都不超过限购**
- 压测准备：批量造用户、**预先生成 Token**。bcrypt 一次要几十毫秒，压测不能走登录接口
- 第一次压测，记录 QPS、P99，以及 MySQL 在高并发下的表现（行锁等待、连接数）

**验收标准**
- 并发测试稳定通过（多跑几次，并开启 `-race`）
- 有一份 baseline 压测记录（写明机器环境和参数）

**面试收获**：能讲清超卖原因和三种锁方案的取舍，也能用数据说明"为什么单靠 MySQL 扛不住秒杀"。

### 阶段 3：Redis 前置拦截（仍然同步落库）

**目标**：把绝大部分请求挡在 Redis，MySQL 只处理真正能成交的请求。

**要做的事**
- **活动预热**：把活动库存、限购配置加载进 Redis
  - 预热发生在"发布之后、开始之前"。阶段 1 规定发布后配置冻结，所以预热进去的数据不会过期
  - 区分"首次初始化"和"故障恢复"，**进行中的活动不允许破坏性重置**（R06）
  - 预热用的分布式锁要带持有者 token，用 Lua 比较后再删除（R15）
  - 活动下线时，Redis 一侧也要停止接单
- **Lua 原子脚本**：在一个脚本里完成活动时间校验、限购校验、扣库存、记录本次预占（以**订单号**为单位）
- 本地内存的"已售罄"标记，售罄后直接在进程内拒绝请求
- Redis 预占成功后**同步**写 MySQL；MySQL 失败时回滚 Redis 预占
- Redis 不可用时快速失败，**不能默认放行**，也不能把 Redis 故障当成"库存为 0"（R17）
- 写**对账脚本 v1**：比对 Redis 剩余库存、MySQL 库存和订单数量

**验收标准**
- 并发测试结束后对账一致
- 压测对比阶段 2，有明确的提升数据，并能解释提升来自哪里

### 阶段 4：异步削峰（引入 MQ + Worker），核心难点

**目标**：把落库从请求链路中拆出去，同时保证**接受过的请求，最终要么生成订单，要么被明确释放**，不允许凭空消失。

**要做的事**
- 链路改造：API 生成订单号 → 完成 Redis 预占 → 投递消息 → 返回"排队中"和订单号 → Worker 消费并落库 → 客户端用订单号轮询结果
- docker-compose 加入 Kafka（也可以选 RocketMQ / RabbitMQ / Redis Stream，选定后要能说清理由；Go 客户端库的选择同理）
- **可靠投递**（R01），以下方案选一种并能讲清楚：
  - 同步发送并等待 broker 确认（如 `acks=all`），失败则回滚 Redis 预占后再返回
  - 或者先持久化预占记录 / 本地消息表，再由后台投递和重放
  - **不要**把消息塞进内存 channel 就返回成功
- **幂等消费**（R03、R09）：以**订单号**作为消息身份；扣库存和插入订单放在同一个 DB 事务里；重复消息表现为主键冲突。Redis 只做加速，不作为"已处理"的最终依据
- **offset 管理**（R02）：业务处理成功后再提交 offset；如果并发或批量处理，必须按分区维护连续的提交水位
- **批次部分失败**（R08）：逐单精确处理，失败的那一单生成补偿（释放预占），不能"按总数截断"
- 重试和死信：多次处理失败的消息进入死信，并有人工或自动的处理入口
- 优雅停机：API 停机前确保已接受的请求都已投递；Worker 处理完当前批次、提交后再退出
- 订单表用迁移加上各环节的时间戳（受理时间等），给阶段 8 统计端到端耗时用

**验收标准（故障注入）**
- 在下面几种情况下，最终都满足 `已接受请求数 = 已落库订单数 + 已明确释放数`：
  - `kill -9` API
  - `kill -9` Worker（包括在落库事务提交前）
  - 停掉 Kafka 一段时间后再恢复
  - 人为制造重复投递
- 对账脚本通过

**面试收获**：这一阶段是项目的核心亮点，"消息丢了怎么办""重复消费怎么办""offset 怎么提交"这些问题都能用自己的设计和测试来回答。

### 阶段 5：订单生命周期与库存补偿，核心难点

**目标**：支付、取消、超时之间不出现竞态，取消后的库存一定能还回去。

**要做的事**
- **订单状态机**：待支付 → 已支付 / 已取消。所有状态转换都用 CAS：`UPDATE ... WHERE id = ? AND status = 待支付`，并检查 `RowsAffected == 1`，只有转换成功的一方才能执行后续动作（R04、R07）。阶段 1 的活动发布 / 下线已经用同样的写法练过一遍
- 模拟支付接口（自身要幂等）
- **超时取消**：
  - 快速触发：延迟消息或 Redis ZSET，采用"领取 → 处理 → 确认"的模式，不要先删再处理（R10）
  - 兜底：DB 定时扫描超时的待支付订单（用阶段 1 建好的 `(status, expire_at)` 索引）
- **可靠库存补偿**（R05）：取消订单时，在**同一个事务**里写入"补偿任务 / 库存流水"；由后台任务幂等地回补 MySQL 库存、Redis 库存和限购额度，失败可重试
- 活动发布后要调整库存，只能走这里的**增量调整**接口并记录流水，不允许直接覆盖绝对值（R11）

**验收标准**
- 并发执行支付和取消（包括超时取消），只会出现一个合法的最终状态，且库存补偿和状态一致
- 注入补偿失败（如补偿时 Redis 宕机），恢复后最终一致
- 对账公式（无在途请求时）：`total_stock = available_stock + SUM(待支付和已支付订单的 quantity)`

### 阶段 6：流量治理与防刷

**目标**：在异常流量下保护系统，并保证正常请求的体验。

**要做的事**
- 多层限流：入口层（Nginx 或网关）、服务级全局令牌桶、用户级限流（Redis Lua）
- 防刷：同一用户的重复请求去重；可选做动态秒杀地址或验证码
- 本地缓存：活动信息、售罄标记，需要设计失效策略
- 降级与快速失败：Redis 或 MQ 异常时返回明确错误，不能把请求堆积在服务里
- 可选：Token 吊销 / 用户封禁。阶段 1 的无状态 JWT 签发后收不回来，在这里补

**验收标准**
- 超出阈值的请求被快速拒绝，正常请求的延迟不受明显影响（压测对比）

---

### 阶段 7：可观测性与质量门禁

**目标**：系统发生了什么能看见，代码质量有自动化保障。

**要做的事**
- Prometheus 指标：接口 QPS 和延迟、预占接受数、MQ 消费积压（lag）、落库 TPS、补偿任务积压、死信数量、数据库连接池（`sqlDB.Stats()`）；配套 Grafana 面板
- 日志中贯穿 `request_id` 和订单号，能串起一个请求从受理到落库的完整链路
- 定时对账任务，不一致时告警（先打日志也可以）
- CI：`gofmt` / `golangci-lint`、`go test -race ./...`、集成测试

**验收标准**
- 在面板上能看到一次秒杀从请求到落库的全过程和积压变化
- 提交代码时 CI 自动跑完测试

---

### 阶段 8：压测、优化与成果沉淀

**目标**：用可信的数据和文档，把前面的工作变成能写进简历、能经得住追问的成果。

**要做的事**
- 用 k6 压测，并**区分统计口径**（R14）：HTTP QPS、预占接受 QPS、落库 TPS、端到端完成耗时、P95/P99，以及压测后的对账结果
- 性能优化，每项都做 A/B 对比并记录：
  - 批量消费和批量插入、连接池调优、分区数和消费并发、pprof 定位热点、热点库存分段（可选）
  - GORM 层面：`SkipDefaultTransaction`（默认每次写操作都包一层 `BEGIN` / `COMMIT`）、`PrepareStmt` 或 DSN 的 `interpolateParams`
- 可选扩展：API 多实例部署（注意订单号生成器 worker id 的分配）、一个简单的前端页面
- 文档：README、架构图、关键设计决策记录（为什么选这个方案、放弃了什么）、压测报告（环境、参数、结果、对账）

**验收标准**
- 有一份可以复现的压测报告，其中每个数字都对应明确的口径和环境
- 能用 3~5 条简历描述概括项目，并且每条都有代码和测试作为支撑

**简历提醒**：没有自己测过的 QPS、P99、"零超卖"，不要写进简历。

## 四、变更记录

### 2026-11-13：阶段 0 完成后的复盘

起因：阶段 0 做完，数据库访问层选了 GORM（原先推荐 `database/sql` + sqlx）。读完 `implement/` 的代码后，对后面的规划做了下面这些调整。

| 改动 | 原因 |
|---|---|
| 新增 1.4「贯穿全程的约定」，其中的 GORM 使用约定是重点 | 原来推荐手写 SQL，是因为后面到处是"条件更新 + 检查影响行数"。换成 GORM 后要求不变，改由约定保证。GORM 的 `Save`、struct 更新跳过零值等默认行为，正好和这个要求冲突 |
| 业务幂等键从 `request_id` 改名为**订单号**（阶段 1、3、4） | 阶段 0 已经把 `request_id` 用作 HTTP 请求的日志追踪标识，而且允许客户端通过请求头指定。两个东西同名，迟早会被混用 |
| 阶段 1 把模型上的决定写明：单用户表、库存归活动、活动状态只存人为状态、发布即冻结、订单号由应用生成 | 原文只有"活动有时间窗、每人限购数、活动库存"一句话。这些决定后面每个阶段都依赖，放到阶段 3 再改代价很大 |
| 阶段 1 增加"分层落地""GORM 日志和错误翻译""时区约定"，并列出不做的范围 | 都是读阶段 0 代码时发现的遗留问题，见阶段 0 的「完成情况」 |
| 阶段 2 增加订单号生成器、事务边界设计、压测造数准备 | 订单号改成应用生成后，阶段 2 就需要生成器（原来放在阶段 8 的可选项里）。bcrypt 实测一次约 50 毫秒，压测必须预先生成 Token |
| 阶段 2 的限购一条，补上三个已经复现过的坑 | 原文"由数据库约束或事务内校验保证"说得太轻。照直觉写的事务内校验在可重复读下是错的 |
| 阶段 3 把预热和"发布即冻结"、活动下线挂钩 | 配合阶段 1 的活动状态设计 |
| 阶段 5 的对账公式改用具体列名；库存调整改为"增量接口" | 配合阶段 1 的 `total_stock` / `available_stock` |
| 阶段 6 增加可选的 Token 吊销；阶段 7 加连接池指标；阶段 8 加 GORM 层面的优化项 | 阶段 1 选了无状态 JWT，要有地方补它的短板；另两项是阶段 0 问题库里已经埋下的伏笔 |

**没有改的**：阶段的划分和顺序、每个阶段的目标和验收标准、三条原则。
